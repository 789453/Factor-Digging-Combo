### 1.2 DuckDB 读取不应该继续“折腾”，真正的问题是签名和路径混乱

`data.py` 里的 DuckDB 读取逻辑其实已经够用。它维护了 `TABLE_CANDIDATES`，会从 `silver.fact_stock_daily / stock_daily / silver.stock_daily`、`silver.fact_stock_moneyflow / stock_moneyflow / silver.stock_moneyflow`、`silver.fact_stock_cyq_perf / stock_cyq_perf / silver.stock_cyq_perf` 等候选表里找存在的表；读取时用 `pool_json` 注册成 `pool_df`，再 join 到 daily 表；还设置了 `threads=16`、`memory_limit='32GB'`、`preserve_insertion_order=false`，并通过列映射只选择所需字段。这个逻辑是合理的，不应该反复重写。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/data.py "raw.githubusercontent.com"))

DuckDB 官方文档也说明 Python API 可以直接运行 SQL，并且 DuckDB 可以读取多种磁盘和内存格式；配置项可以通过 `SET` 语句设置，`memory_limit` 和 `threads` 都是可配置项，`preserve_insertion_order=false` 的语义也是允许无 ORDER BY 的结果重排以获得优化空间。([DuckDB](https://duckdb.org/docs/current/clients/python/overview.html "Python API – DuckDB"))

真正的问题出在两处：

一是配置路径混乱。`configs/phase2/phase2_coarse_fine.yaml` 里默认 `duckdb_path: data/market.duckdb`，但旧 `run_mining_workflow.sh` 里写的是 Windows 绝对路径 `D:\Trading\data_ever_26_3_14\data\meta\warehouse.duckdb`。这会导致“有的脚本能跑，有的脚本读不到真实数据”，不是 DuckDB 读取逻辑本身的问题。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/configs/phase2/phase2_coarse_fine.yaml "raw.githubusercontent.com"))

二是 `signature.py` 的 `compute_data_signature` 假设存在 `market_data` 表，并使用 `date/code` 字段做统计；而真实 `data.py` 读取逻辑使用的是 `trade_date/ts_code`，并且会从多张候选表 join。这个不一致会让 data signature 变成 `"error"` 或失真，从而影响去重和断点复用。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/signature.py "raw.githubusercontent.com"))

所以结论是：**DuckDB 读取模块不要大改；要修正配置唯一入口和 signature 逻辑**。所有真实数据路径只在一个 YAML 中配置，所有脚本只调用这个 YAML。数据签名也必须复用 `data.py` 的表发现逻辑，而不是另造一个 `market_data/date/code` 假设。

`template_builder.py` 也已经实现了 `build_single`、`build_binary_same_ts`、`build_binary_mixed_ts`、`build_multi_window`、`build_triple_modulation`、`build_quad_balanced`。但三阶、四阶实现仍然偏“演示式”：它在 triple/quad 中用 `random.sample(fields, 3/4)` 选字段，并且当 `spec.ts_ops` 包含 `TsMean` 时，实际只把 A/B/C/D 替换成 `TsMean($f,w)`，没有系统枚举 `TsDelta/TsEMA` 等 `ts_ops`；这会导致 YAML 里写了多个 ts\_ops，但真实表达式空间没有完全覆盖。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/template_builder.py "raw.githubusercontent.com"))

因此，模板方向是对的，但实现要从“随机试探式生成”改成“确定性、可复现、可统计、可控预算”的生成。尤其你强调“因子模板尽量全面一些”，那全面不是靠随机 sample，而是靠明确列出模板族、组合形式、算子组合、窗口组合，然后在表达式数量过大时做稳定 hash 采样。

## 4. DuckDB 正确处理：只修三处，不再反复改读取逻辑

### 4.1 `data.py` 保持为唯一数据读取入口

`load_from_duckdb` 已经能处理表候选、pool join、列选择、真实日期范围、基础表 join。建议不要再新增 `real_data_loader.py`、`duckdb_loader_v2.py` 之类的文件。所有真实数据加载必须走：

```
from .data import load_from_duckdb

```

修正点只有两个：

第一，`load_pool` 要兼容 list 和 dict。当前 `compute_pool_signature` 已经兼容 list 和 dict，但 `data.load_pool` 直接 `json.loads` 返回对象；如果 pool 文件是 `{"codes": [...]}`，后续 `pd.DataFrame({"ts_code": pool})` 会错误。建议：

```
def load_pool(path):
    raw = json.loads(Path(path).read_text(encoding="utf-8"))
    if isinstance(raw, dict):
        return raw.get("codes") or raw.get("ts_codes") or []
    return raw

```

第二，`columns` 参数应接入字段依赖。当前 `load_from_duckdb` 支持 `columns`，但 `phase2_pipeline.py` 没传。后续可以根据 `selected_fields` 的 deps 推导最小列集合，减少 DuckDB IO。

### 4.2 `signature.py` 的 data signature 必须复用真实表结构

现在 `compute_data_signature` 查询 `market_data`、`date`、`code`，这和 `data.py` 的真实表结构不一致。应改成：

```
def compute_data_signature(duckdb_path, pool_json, start, end):
    conn = duckdb.connect(duckdb_path, read_only=True)
    daily = _first_existing_table(conn, TABLE_CANDIDATES["daily"])
    pool = load_pool(pool_json)

    if pool:
        register pool_df
        query count/min/max/count(distinct ts_code)
        from daily d join pool_df p on d.ts_code=p.ts_code
        where d.trade_date between start and end
    else:
        query daily only

    return {
        "duckdb_path_hash": file_sha256_or_path_hash(duckdb_path),
        "daily_table": daily,
        "start": start,
        "end": end,
        "row_count": row_count,
        "min_trade_date": min_date,
        "max_trade_date": max_date,
        "unique_codes": unique_codes,
        "fingerprint": sha256(...)
    }

```

不要再假设 `market_data`。这样“之前真实数据跑通过”的路径可以稳定下来。

### 4.3 DuckDBJobStore 与源 DuckDB 分离

一个容易混淆的点是：你现在有两个 DuckDB：

```
源数据 DuckDB:
  D:/Trading/.../warehouse.duckdb

结果 DuckDB:
  outputs/phase2/.../phase2_results.duckdb

```

这两个不要合并。源 DuckDB 只读；结果 DuckDB 可写，用于 runs、expression\_catalog、expression\_jobs、factor\_results、attribution。`DuckDBJobStore` 当前已经用 DuckDB 管理结果表，这个方向是对的。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/job_store.py "raw.githubusercontent.com"))

当前算子体系已经包含 `Abs/SLog1p/Inv/Sign/Log/Rank`，二元包含 `Add/Sub/Mul/Div/Pow/Greater/Less`，rolling 包含 `TsMean/TsSum/TsStd/TsIr/TsMinMaxDiff/TsMaxDiff/TsMinDiff/TsVar/TsSkew/TsKurt/TsMax/TsMin/TsMed/TsMad/TsRank/TsDelta/TsDiv/TsPctChange/TsWMA/TsEMA`，pair rolling 包含 `TsCov/TsCorr`。这说明模板本身可以比当前 YAML 更完整，但高成本算子如 `TsSkew/TsKurt/TsMad/TsMed` 应放在 heavy family 或低采样率中。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/ops.py "raw.githubusercontent.com"))

建议 `templates_v2.yaml` 中：

```

  - name: single_ts_core
    family: single
    unary_pre: [Id, Abs, SLog1p]
    ts_ops: [TsMean, TsStd, TsIr, TsRank, TsDelta, TsDiv, TsPctChange, TsWMA, TsEMA, TsMinMaxDiff]
    outer_transforms: [Rank, SLog1p, RankSLog1p]

  - name: single_ts_ext
    family: single
    enabled: true
    sample_rate: 0.25
    unary_pre: [Id]
    ts_ops: [TsMaxDiff, TsMinDiff, TsVar, TsMax, TsMin]
    outer_transforms: [Rank]

  - name: binary_same_ts_core
    family: binary_same_ts
    ts_ops: [TsMean, TsStd, TsIr, TsRank, TsDelta, TsEMA, TsWMA]
    binary_ops: [Add, Sub, Mul, Div, Greater, Less]
    outer_transforms: [Rank]

  - name: binary_mixed_ts_core
    family: binary_mixed_ts
    left_ts_ops: [TsMean, TsDelta, TsEMA, TsIr]
    right_ts_ops: [TsMean, TsStd, TsRank, TsWMA, TsMinMaxDiff]
    binary_ops: [Sub, Div, Mul]
    outer_transforms: [Rank]

  - name: pair_corr_cov
    family: pair_rolling
    pair_ops: [TsCorr, TsCov]
    outer_transforms: [Rank, SLog1p]
    sample_rate: 0.35

  - name: multi_window_gap
    family: multi_window
    short_windows: [5, 10, 20]
    long_windows: [30, 40, 60]
    ts_ops: [TsMean, TsEMA, TsStd, TsRank]
    binary_ops: [Sub, Div]
    outer_transforms: [Rank]

  - name: triple_modulation_core
    family: triple
    ts_ops: [TsMean, TsDelta, TsEMA]
    forms:
      - Rank(Mul(Sub(A,B),C))
      - Rank(Div(Sub(A,B),Abs(C)))

      - Rank(Mul(Div(A,B),C))
    sample_rate: 0.08
    max_count: 30000

    family: quad

    sample_rate: 0.02

```

### 5.2 builder 必须改成确定性枚举 + hash 采样

当前 triple/quad 使用 `random.sample`，不利于解释每个模板组合的有效性。建议改成：

```
for field_tuple in combinations(fields, 3):
    for w in windows:
        for ts_op in spec.ts_ops:
            for form in spec.forms:
                key = f"{spec.name}|{form}|{ts_op}|{w}|{field_tuple}"
                if not stable_keep(key, spec.sample_rate, seed):
                    continue
                A = f"{ts_op}(${f1},{w})"
                B = f"{ts_op}(${f2},{w})"
                C = f"{ts_op}(${f3},{w})"
                expr = render_form(form, A=A, B=B, C=C)

```

四阶用 `combinations(fields, 4)`，但采样率更低。这样每个表达式来源可复现，后续 attribution 才有意义。

### 5.3 增加 template\_combo\_catalog

必须把“模板组合”列出来，而不只是表达式结果。新增表：

```
template_combo_catalog(

  template_family,
  form,
  ts_op,
  left_ts_op,
  right_ts_op,
  pair_op,

  outer_transform,

  long_window,
  n_generated,
  n_valid,
  n_evaluated,
  n_ok,
  median_score_ranked,
  top5pct_rate
)

```

这样你能回答：


这比只看字段和算子更接近你关心的“模板逻辑有效性”。

## 7. 性能和消耗速度：现有方向对，但要减少重复计算与数据传输

### 7.1 继续使用矩阵 panel + Numba

`TEMPLATES_EXPLAINED.md` 已经说明项目使用 `(T, N)` 的 NumPy 矩阵面板，优势是避开 Pandas 索引对齐开销、适配 Numba 并行、降低内存碎片和 IO 传输损耗。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/TEMPLATES_EXPLAINED.md "raw.githubusercontent.com"))

`ops.py` 当前已经把很多 rolling 算子切到 `fastops`，包括 rolling mean/sum/std/max/min/rank/wma/corr；`fastops.py` 使用 `numba.njit(cache=True, parallel=True)` 和 `prange` 实现多处加速。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/ops.py "raw.githubusercontent.com"))

Numba 文档说明 `parallel=True` 会尝试自动并行化和优化部分函数，尤其对 CPU 上的数组操作和循环有帮助。([numba.pydata.org](https://numba.pydata.org/numba-doc/dev/user/parallel.html?utm_source=chatgpt.com "Automatic parallelization with @jit"))

这条路对，不要改回 pandas 回测式逐因子流程。

### 7.2 先做 primitive cache

模板全面化后，高阶表达式会大量重复子表达式：

```
TsMean($f,20)
TsDelta($f,20)
TsEMA($f,20)
Rank(TsMean($f,20))

```

建议新增：

```
src/alpha_mvp/primitive_cache.py

```

缓存 key：

```
primitive_hash = sha256(run_signature_without_expr + operator + field + window)

```

粗筛和细筛都可以复用同一 run 内 primitive。这样三阶、四阶模板只做组合，不反复 rolling。

### 7.3 控制 BatchEvaluator cache 生命周期

当前 `BatchEvaluator` 有 cache，但大规模表达式会导致 cache 增长。建议配置：

```
runtime:
  evaluator_cache:
    keep_primitives: true
    clear_composite_every_batches: 20
    max_items: 8000

```

### 7.4 结果 DuckDB 批量写入

`job_store.write_results` 当前逐行执行 SQL。表达式数上来后，建议改成：

```
df = pd.DataFrame(results)
con.register("tmp_results", df)
con.execute("""
INSERT OR REPLACE INTO factor_results
SELECT ...
FROM tmp_results
""")

```

DuckDB Python API 支持把 Python 对象作为关系参与 SQL 查询，适合这种批量写入模式。([DuckDB](https://duckdb.org/docs/current/clients/python/overview.html "Python API – DuckDB"))
