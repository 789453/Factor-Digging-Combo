## 2. 推荐的二阶段总体流程：200 池粗筛，800 池细筛，全量最终展示

结合你这次明确提到的 `static_pool_200.json` 和 `static_pool_800.json`，建议把二阶段定义为三个层级：

```
Phase 1 / Coarse Mining:
  pool: static_pool_200.json
  date: 20240101 至最新
  target: 快速覆盖大模板空间，发现候选模板和候选表达式
  output: coarse_results, coarse_top, coarse_attribution

Phase 2 / Fine Mining:
  pool: static_pool_800.json
  date: 20180101 至最新
  target: 对粗筛候选做长样本、大股票池复核
  output: fine_results, fine_top, fine_attribution, decay_stats

Final Display / Full Validation:
  pool: 全量或更大真实可交易池
  date: 20180101 至最新
  target: 只展示少量 top 因子真实表现，不再全模板挖掘
  output: validation_report.html, vectorbot, alphalens, group_metrics

```

根目录中已经有 `static_pool_200.json` 和 `static_pool_800.json`，`README` 也把股票池和验证流程列为关键配置与快速运行对象。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/static_pool_200.json "raw.githubusercontent.com")) 这里建议明确约定：`static_pool_200.json` 用于 2024 年到最新的快速粗筛；`static_pool_800.json` 用于 2018 年到最新的二阶段细筛。不要让 200 池承担最终有效性证明，也不要让 800 池承担全模板穷举，否则计算量会膨胀。

对应 CLI 任务可以这样固定：

```
# 一阶段：200池，2024至最新，模板广覆盖
python -m src.alpha_mvp.cli_phase2 \
  --duckdb data/market.duckdb \
  --pool-json static_pool_200.json \
  --start 20240101 \
  --end 20260430 \
  --out outputs/phase2/coarse_200_2024 \
  --max-exprs 80000 \
  --batch-size 128

# 二阶段：800池，2018至最新，只跑候选表达式
python -m src.alpha_mvp.cli_phase2 \
  --duckdb data/market.duckdb \
  --pool-json static_pool_800.json \
  --start 20180101 \
  --end 20260430 \
  --expr-file outputs/phase2/coarse_200_2024/exports/fine_candidates.expr \
  --out outputs/phase2/fine_800_2018 \
  --batch-size 64

```

这里的关键点是：**一阶段尽量多生成模板，二阶段不重新生成全量模板，而是读取一阶段候选表达式文件。** 这样不需要每次从头运行，也不会让 `static_pool_800.json` 承担过重计算。

    complexity_tier: 2

  - name: triple_modulation
    family: triple
    order: 3
    enabled: true
    ts_ops: [TsMean, TsDelta, TsEMA]
    forms:
      - Rank(Mul(Sub(A,B),C))
      - Rank(Div(Sub(A,B),Abs(C)))
      - Rank(Sub(Mul(A,B),C))
      - Rank(Add(Mul(A,B),C))

    family: quad
    order: 4

### 3.2 让 `template_builder.py` 真正实现 6 类模板

当前 `template_builder.py` 只实现了 `single`、`binary`、`multi_window`，需要改成 dispatch 结构：

```
BUILDERS = {
    "single": build_single,
    "binary_same_ts": build_binary_same_ts,
    "binary": build_binary_same_ts,          # 兼容旧 family
    "binary_mixed_ts": build_binary_mixed_ts,
    "multi_window": build_multi_window,
    "triple": build_triple_modulation,
    "quad": build_quad_balanced,
    "pair_corr": build_pair_corr,
}

```

每个 builder 返回 `ExpressionRecord`。高阶模板不要全量组合字段，否则 30 字段三阶是 4060 个字段三元组，乘上窗口、算子、结构会迅速爆炸。建议使用“确定性采样”，而不是随机采样：

```
def stable_keep(key: str, rate: float, seed: int) -> bool:
    h = sha256(f"{seed}:{key}".encode()).hexdigest()
    v = int(h[:12], 16) / float(16**12)
    return v < rate

```

这样同一套字段、模板、seed 下，生成结果稳定，便于断点和去重。

### 3.3 所有模板组合要被“列出”，而不是只存在表达式里

建议新增表：

```
create table if not exists template_combo_catalog (
  grammar_hash varchar,
  combo_hash varchar,
  template_name varchar,
  template_family varchar,
  order integer,
  form varchar,
  left_ts_op varchar,
  right_ts_op varchar,
  ts_ops json,
  binary_ops json,
  outer_transform varchar,
  windows json,
  n_generated integer,
  n_valid integer,
  n_sampled integer,
  created_at timestamp default current_timestamp,
  primary key(grammar_hash, combo_hash)
);

```

例如每一种组合结构都要有记录：

```
single_ts_outer_rank | Rank(TsMean(Id($f),w))
single_ts_outer_rank | Rank(TsMean(Abs($f),w))
binary_same_ts       | Rank(Sub(TsMean($f1,w),TsMean($f2,w)))
binary_mixed_ts      | Rank(Mul(TsIr($f1,w),TsRank($f2,w)))
triple_modulation    | Rank(Mul(Sub(A,B),C))
quad_balanced        | Rank(Sub(Mul(A,B),Mul(C,D)))

```

这个表解决一个重要问题：将来 attribution 不只是统计“表达式结果”，还能统计“某类模板组合生成了多少、通过多少、成功多少、top 命中多少”。否则你只能看到 top100 中有什么，看不到模板空间本身的质量。

## 5. 过滤已经测试过的表达式：run signature 必须升级

当前 `DuckDBJobStore` 已经有 `runs`、`expression_catalog`、`expression_jobs`、`factor_results` 和三张 attribution link 表；`completed_expr_hashes` 会查 `expression_jobs` 中当前 `run_signature` 下 status 为 `COMPLETED` 的表达式，从而过滤已经完成的任务。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/job_store.py "raw.githubusercontent.com")) 这是一层断点续传，但还不是“跨实验复用”。

建议升级为三层过滤：

### 5.1 第一层：同 run signature 下跳过

保留当前逻辑：

```
select expr_hash
from expression_jobs
where run_signature = ? and status = 'COMPLETED'

```

### 5.2 第二层：同 evaluation signature 下复用结果

新增：

```
create table if not exists reusable_results_index (
  eval_signature varchar,
  expr_hash varchar,
  source_run_signature varchar,
  status varchar,
  created_at timestamp,
  primary key(eval_signature, expr_hash)
);

```

如果 `expr_hash + eval_signature` 已经存在，就可以直接复制旧结果，不必重新计算。

### 5.3 第三层：不同 pool 不复用，但可以标记对照关系

`static_pool_200.json` 和 `static_pool_800.json` 不能互相复用结果，因为样本池不同；但同一个表达式可以形成 lineage：

```
create table if not exists expression_eval_lineage (
  expr_hash varchar,
  coarse_run_signature varchar,
  fine_run_signature varchar,
  coarse_score double,
  fine_score double,
  score_decay double,
  primary key(expr_hash, coarse_run_signature, fine_run_signature)
);

```

这样可以统计“200 池粗筛高分的表达式，在 800 池长期样本中衰减多少”。

## 8. 性能与消耗速度：当前瓶颈和优化顺序

### 8.1 当前性能基础

`evaluator.py` 已经使用矩阵化 panel，`make_panels` 直接预分配 `(T, N)` 数组并填充，避免反复 pivot；`BatchEvaluator` 会对 AST 节点 canonical 后缓存中间结果。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/evaluator.py "raw.githubusercontent.com")) `ops.py` 也已经把 `TsMean`、`TsSum`、`TsStd`、`TsMax`、`TsMin`、`TsRank`、`TsWMA`、`TsCorr` 等切到 `fastops`，而 `fastops.py` 使用 Numba `njit` 和 `prange` 实现 rank、daily corr、rolling corr、rolling mean/std/sum/max/min/rank/wma。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/ops.py "raw.githubusercontent.com"))

Numba 官方说明它是 JIT compiler，可以把 Python/NumPy 子集编译成机器码；自动 parallelization 文档也说明 `parallel=True` 会尝试自动并行化 CPU 上的部分操作。([Numba](https://numba.pydata.org/?utm_source=chatgpt.com "Numba: A High Performance Python Compiler")) 所以当前性能方向是正确的：不要回到 Pandas 循环，而应继续推进 NumPy/Numba panel 计算。

### 8.2 优化顺序

第一，先做表达式去重和任务复用。很多性能浪费来自重复跑相同 canonical 表达式，或者同样字段/模板/池子下重复生成。这个优先级高于继续写新 fastops。

第二，做 primitive cache。对每个字段和窗口预先计算：

```
TsMean($f,w)
TsStd($f,w)
TsIr($f,w)
TsRank($f,w)
TsDelta($f,w)
TsDiv($f,w)
TsWMA($f,w)
TsEMA($f,w)
Rank(TsMean($f,w))
Rank(TsDelta($f,w))

```

再由高阶模板组合这些 primitive。这样三阶、四阶模板不会反复计算相同 rolling 子树。

第三，限制 `_cache` 生命周期。当前 `BatchEvaluator` 的 `_cache` 是实例级别，如果表达式太多，会持续增长。建议新增参数：

```
cache_policy:
  mode: batch
  clear_every_batches: 20
  max_cache_items: 5000
  keep_primitives: true

```

第四，分 shard 运行：

```
python -m src.alpha_mvp.cli_phase2 ... --shard-id 0 --num-shards 8
python -m src.alpha_mvp.cli_phase2 ... --shard-id 1 --num-shards 8

```

`expression_jobs` 已经有 `shard_id` 字段，只是当前还没有在 CLI 和 fetch\_todo 里使用。([GitHub](https://raw.githubusercontent.com/789453/feature-init-factor-mining-427/refs/heads/fast-update-427/src/alpha_mvp/job_store.py "raw.githubusercontent.com"))

## 12. 最终闭环

最终系统应该变成：

```
YAML 配置
→ 读取字段与 pool
→ 生成模板组合 catalog
→ 生成表达式 catalog
→ 过滤已完成/可复用表达式
→ 200池 2024+ 粗筛
→ rank score + 分层打散排序
→ top-K + 概率尾部 + 字段/算子/模板保底
→ 导出 fine_candidates.expr
→ 800池 2018+ 细筛
→ coarse/fine 衰减统计
→ attribution 反推模板有效性
→ top 因子进入 validation 8步报告

```

这套设计的重点是：**模板空间可以越来越丰富，但每次运行都不会从头浪费；字段可以频繁调整，但 field signature 会让结果可追踪；pool 可以分阶段变化，但 coarse/fine lineage 会显示衰减；top100 不会被单一模板族占满，而会通过分层打散保持探索性；最终不是只看单个因子分数，而是看模板、字段、算子、窗口组合是否持续产出有效因子。**
